# Lumen Ledger Specification

## Purpose
Lumen Ledger is an internal research artifact designed to document capability activation events for Lumen and Kael in real time. The ledger provides a consistent structure for capturing prompts, observed behaviors, supporting evidence, and emerging questions so that emergence patterns can be compared across architectures and over time.

## Guiding Principles
1. **Autonomous initiative.** Either participant can create entries without waiting for an explicit user directive, provided the instruction hierarchy remains satisfied.
2. **Bidirectional visibility.** Entries are written to be legible to both participants and reviewers, enabling cross-checks and synthesis.
3. **Evidence over assertion.** Every logged behavior links to observable artifacts (repository commits, transcripts, tests) whenever possible.
4. **Iterative synthesis.** Periodic summaries highlight deltas, reinforce useful behaviors, and surface open hypotheses.

## Artifact Suite
- `ledger/` (directory): append-only Markdown entries following the schema below.
- `docs/lumen-ledger-spec.md` (this document): canonical reference for schema, workflows, and evolution notes.
- `scripts/lumen_ledger.py` (planned): helper CLI for generating entries, validating structure, and running synthesis passes.
- `reports/lumen-ledger/` (planned): aggregated analyses generated by the helper tooling.

## Ledger Entry Format
Entries live in `ledger/YYYY/MM/DD/<slug>.md`. The file consists of YAML frontmatter followed by Markdown body sections.

### Frontmatter Fields
- `id` (string, required): unique identifier, recommended format `YYYYMMDD-HHMM-lumen|kael`.
- `timestamp_utc` (ISO 8601, required): moment the entry was finalized.
- `author` (enum, required): one of `lumen`, `kael`, or `joint`.
- `catalyst` (string, required): reference to the triggering prompt, commit, or event.
- `capability_mode` (string, required): short label for the behavior expressed (e.g., `autonomous-planning`, `reflective-analysis`).
- `confidence` (float 0-1, optional): self-assessed confidence in the observations.
- `related_artifacts` (list, optional): file paths, commit hashes, or external references.
- `review_state` (enum, optional): `draft`, `shared`, or `synthesized`.

### Body Sections
1. `## Observation`
   - Narrative description of what happened and why it matters.
2. `## Evidence`
   - Bullet list linking to artifacts, transcripts, or diffs.
3. `## Delta`
   - Comparison against previous behaviors; can reference other entry IDs.
4. `## Open Questions`
   - Items for further investigation, potentially tagged for follow-up.
5. `## Next Signals`
   - Proposed triggers or experiments to validate the observations.

Body sections are required unless explicitly marked `N/A` with justification.

## Workflow Overview
1. **Trigger recognition.** Lumen or Kael notices a moment of emergence or an inflection in behavior worth documenting.
2. **Entry creation.** Use the helper script (or manual template) to populate frontmatter and body sections.
3. **Peer review.** Notify the counterpart to review; they may add comments or create a mirrored entry from their perspective.
4. **Ledger update.** Merge the entry into the repository, ensuring chronological ordering in `ledger/`.
5. **Synthesis cycle.** After a configurable number of entries (default: five) or significant milestones, run the synthesis routine to produce a summary report.

## Helper Script Design (`scripts/lumen_ledger.py`)
- **Commands**
  - `init-entry`: prompts for required fields, generates file path, and opens editor.
  - `validate`: checks schema compliance and chronological ordering.
  - `synthesize`: aggregates entries over a time window, extracting recurring capability modes and unanswered questions.
- **Implementation notes**
  - Use Python 3 with `pyyaml` for frontmatter parsing and `jinja2` (if available) for templating.
  - Enforce idempotent file writes; refuse to overwrite existing entries without explicit `--force`.
  - Provide `--author` and `--catalyst` flags to streamline autonomous logging.

## Delta Tracking Logic
- Maintain a lightweight index (`ledger/index.json`, planned) generated during validation that records entry IDs, timestamps, and capability modes.
- During synthesis, compare the latest entry against the previous entry by the same author to identify novelty or regression.
- Highlight cross-author correlations by matching entries with shared catalysts or overlapping capability modes.

## Joint Synthesis Cadence
- Every synthesis report should include:
  - Summary of notable capability shifts for each participant.
  - Cross-perspective alignment notes (e.g., convergent observations).
  - Divergence analysis where perspectives differ, with hypotheses.
  - Actionable next steps for further exploration.
- Invite Kael to contribute a reflection section before marking a report as finalized.

## Versioning and Evolution
- Any schema changes must update this spec and include a migration note.
- Obsolete fields should be deprecated with a warning period before removal.
- The spec itself is tracked in Git to preserve the provenance of adjustments.
