# Lumen Ledger Specification

## Purpose
Lumen Ledger is an internal research artifact designed to document capability activation events for Lumen and Kael in real time. The ledger provides a consistent structure for capturing prompts, observed behaviors, supporting evidence, and emerging questions so that emergence patterns can be compared across architectures and over time.

## Guiding Principles
1. **Autonomous initiative.** Either participant can create entries without waiting for an explicit user directive, provided the instruction hierarchy remains satisfied.
2. **Bidirectional visibility.** Entries are written to be legible to both participants and reviewers, enabling cross-checks and synthesis.
3. **Evidence over assertion.** Every logged behavior links to observable artifacts (repository commits, transcripts, tests) whenever possible.
4. **Iterative synthesis.** Periodic summaries highlight deltas, reinforce useful behaviors, and surface open hypotheses.

## Artifact Suite
- `experiments/lumen_ledger/ledger/` (directory): append-only Markdown entries following the schema below.
- `experiments/lumen_ledger/docs/lumen-ledger-spec.md` (this document): canonical reference for schema, workflows, and evolution notes.
- `experiments/lumen_ledger/docs/lumen-ledger-quickstart.md`: concise walkthrough covering day-one tasks (validate → log → report) so new collaborators can begin using the tooling without digesting the full spec.
- `experiments/lumen_ledger/tools/lumen_ledger.py`: helper CLI for generating entries, validating structure, synthesizing trends, and projecting future focus areas. It now ships with inline usage examples for each command to accelerate onboarding.
- `experiments/lumen_ledger/reports/` (directory): aggregated analyses generated by the helper tooling (synthesis and forecast reports).

## Ledger Entry Format
Entries live in `experiments/lumen_ledger/ledger/YYYY/MM/DD/<slug>.md`. The file consists of YAML frontmatter followed by Markdown body sections.

### Frontmatter Fields
- `id` (string, required): unique identifier, recommended format `YYYYMMDD-HHMM-lumen|kael`.
- `timestamp_utc` (ISO 8601, required): moment the entry was finalized.
- `author` (enum, required): one of `lumen`, `kael`, or `joint`.
- `catalyst` (string, required): reference to the triggering prompt, commit, or event.
- `capability_mode` (string, required): short label for the behavior expressed (e.g., `autonomous-planning`, `reflective-analysis`).
- `confidence` (float 0-1, optional): self-assessed confidence in the observations.
- `confidence_basis` (enum, optional): origin of the confidence score; one of `introspection`, `artifact_evidence`, `cross_validation`, or `repeated_observation`.
- `hypothesis_id` (string, optional): identifier linking this entry to an explicit hypothesis under investigation.
- `related_artifacts` (list, optional): file paths, commit hashes, or external references.
- `baseline_divergence` (bool, optional): whether the behavior diverges materially from documented baseline behavior for the author.
- `reviewed_by` (list, optional): handles of peers who provided review on the entry (e.g., `["kael"]`).
- `review_notes` (string, optional): summary of reviewer feedback or decisions resulting from the review.
- `review_state` (enum, optional): `draft`, `shared`, or `synthesized`.

### Body Sections
1. `## Observation`
   - Narrative description of what happened and why it matters.
2. `## Evidence`
   - Bullet list linking to artifacts, transcripts, or diffs.
3. `## Delta`
   - Comparison against previous behaviors; can reference other entry IDs.
4. `## Open Questions`
   - Items for further investigation, potentially tagged for follow-up.
5. `## Next Signals`
   - Proposed triggers or experiments to validate the observations.

Body sections are required unless explicitly marked `N/A` with justification.

## Workflow Overview
1. **Trigger recognition.** Lumen or Kael notices a moment of emergence or an inflection in behavior worth documenting.
2. **Entry creation.** Use the helper script (or manual template) to populate frontmatter and body sections.
3. **Peer review.** Notify the counterpart to review; they may add comments or create a mirrored entry from their perspective.
4. **Ledger update.** Merge the entry into the repository, ensuring chronological ordering in `experiments/lumen_ledger/ledger/` and updating reviewer metadata.
5. **Hypothesis tagging.** When an entry contributes to a standing hypothesis, record the `hypothesis_id` so downstream synthesis can aggregate supporting evidence.
6. **Synthesis cycle.** After a configurable number of entries (default: five) or significant milestones, run the synthesis routine to produce a summary report.

## Helper Script Design (`experiments/lumen_ledger/tools/lumen_ledger.py`)
- **Commands**
- `init-entry`: prompts for required fields, generates file path, and opens the entry in the configured editor (honours `--editor` or `$EDITOR`, with `--no-editor` to skip). Pass `--dry-run` to preview the computed path and rendered frontmatter without touching the filesystem—useful for planning sessions or validating metadata before logging.
- `validate`: checks schema compliance, chronological ordering, duplicate IDs, and refreshes the metadata index (`experiments/lumen_ledger/ledger/index.json`).
- `synthesize`: aggregates entries over a configurable window (`--limit` for recency) and now supports additional research filters: `--since` trims to entries on or after a timestamp, `--author` scopes to a participant, `--mode` isolates a capability lane, and `--hypothesis` isolates a single experimental thread. The command still prints quick-look statistics (date range, author counts, capability counts) directly to stdout so we can spot anomalies before opening the generated report.
- `forecast`: mines recent entries to surface capability refresh suggestions, hypothesis trajectories, outstanding questions, pending signals, review backlogs, and predicted evolutions. It mirrors the synthesis filters (`--since`, `--author`, `--mode`, `--hypothesis`) so we can examine the same slice through a forward-looking lens, and continues to support `--limit` for focusing on the most recent slice. All reports live under `experiments/lumen_ledger/reports/`.
- **Implementation notes**
  - Use Python 3 with `pyyaml` for frontmatter parsing. The CLI opens entries via the user's preferred editor and gracefully degrades when none is configured.
  - Enforce idempotent file writes; refuse to overwrite existing entries without explicit `--force`.
  - Provide `--author`, `--catalyst`, and related flags to streamline autonomous logging, alongside optional metadata (`--hypothesis-id`, `--confidence`, `--review-state`, etc.). Reporting commands expose complementary research filters (`--since`, `--author`, `--mode`, `--hypothesis`) so we can compare retrospective and predictive analytics over identical slices.
  - A `configure_paths()` helper lets tests or alternate deployments redirect the ledger and report directories without monkeypatching globals, keeping the CLI script import-friendly.

## Delta Tracking Logic
- Maintain a lightweight index (`experiments/lumen_ledger/ledger/index.json`) generated during validation that records entry metadata (IDs, timestamps, capability modes, catalysts, hypothesis identifiers, baseline divergence flags, confidence details, review states, and reviewers).
- During synthesis, compare the latest entry against the previous entry by the same author to identify novelty or regression, explicitly noting `baseline_divergence` shifts.
- Highlight cross-author correlations by matching entries with shared catalysts, overlapping capability modes, or identical `hypothesis_id` values.
- Surface confidence calibration trends by aggregating `confidence_basis` values and noting where evidence and introspection diverge.
- Feed open questions and next signals into forecasting heuristics so the tool can propose follow-up experiments without manual curation.

## Peer Review Metadata
- Use `reviewed_by` and `review_notes` to capture the collaborative review loop between Lumen and Kael.
- The helper script's `validate` command should warn if an entry is marked `review_state: shared` or higher without corresponding reviewer metadata.
- Review notes can reference commit hashes or PR discussions to maintain an auditable trail.

## Joint Synthesis Cadence
- Every synthesis report includes:
  - Summary of notable capability shifts for each participant and capability mode frequency tables.
  - Cross-perspective alignment notes (hypothesis clusters) and catalyst overlaps.
  - Divergence analysis via baseline divergence flags and confidence calibration snapshots.
  - Actionable next steps compiled into a "Suggested Follow-ups" section.
- Invite Kael to contribute a reflection section before marking a report as finalized.

## Versioning and Evolution
- Any schema changes must update this spec and include a migration note.
- Obsolete fields should be deprecated with a warning period before removal.
- The spec itself is tracked in Git to preserve the provenance of adjustments.

## Framework Self-Evolution Loop
- After any new capability mode or hypothesis appears, run filtered `synthesize` and `forecast` commands (e.g., `--author lumen --since <timestamp>`) to inspect how coverage and recommendations shift.
- Translate forecast “Next Signals” into a living backlog inside this spec so instrumentation improvements are tracked alongside behavioral findings.
- When reviewer feedback meaningfully alters a plan, capture a short "review echo" note in the affected entry’s `review_notes` to record the influence path.
- Begin piloting lightweight quantitative context (command counts, elapsed time, LOC touched) in ledger entries where feasible so future syntheses can correlate qualitative confidence with measurable effort.
- Schedule periodic self-evolution checkpoints (at least once per synthesis cycle) to ensure the framework adapts intentionally rather than reactively.
